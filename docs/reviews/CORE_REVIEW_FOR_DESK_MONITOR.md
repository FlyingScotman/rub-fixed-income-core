# Ревью ядра для Trading Desk Monitor

21 октября 2026. Что есть в `rub-fixed-income-core`, насколько точно, чего не хватает целевому
интерфейсу Trading Desk Monitor (TDM) и что сделано в 0.33.0.

| Что | Ревизия |
|---|---|
| Ядро, исходное состояние | `main` `c0af388`, 0.32.0 — коммит, на который TDM ссылается в `backend/pyproject.toml` (`[tool.uv.sources]`) |
| Ядро, результат | ветка `claude/core-tdm-review`, 0.33.0 |
| TDM | ветка `claude/trading-desk-monitor-ui-mhv0gi`: код бэкенда на `fefdb9a`–`9647e37` (ветка двигалась во время ревью; тесты гонялись на снимке `9647e37`) |
| Целевой интерфейс | `prototypes/concepts/` c01–c13, `lib/kit.js`, `lib/mock.js`, `lib/real.js` |
| Запросы владельца и бриф | `docs/program/OWNER_REQUESTS.md` (R8, R14/R15, R18, R24), `docs/architecture/briefs/CORE.md` (C1–C8) |

Метод: чтение кода обеих сторон (что TDM вызывает и что делает сам вместо ядра), сверка с
публичными данными MOEX ISS и ЦБ за 20.10.2026, бенчмарки, прогон тестов TDM на рабочем
дереве ядра. Репозиторий TDM не менялся.

## 1. Вердикт на одной странице

**Ядро готово к целевому интерфейсу почти целиком.** К 0.32.0 закрыты пакеты 0–9 плана:
у каждого продукта интерфейса есть модель, риск в словаре факторов деска, тесты и, где
данные публичны, сверка с MOEX / ЦБ / ISDA. Расхождения с интерфейсом были не в моделях, а в
**аналитике вокруг них**: того, что показывает карточка позиции и страницы рисков, ядро
либо не отдавало, либо отдавало не в той форме, и TDM считал это сам.

**Точность против MOEX (EOD 20.10.2026, свежая сверка, §3)** — без исключений там, где правило
известно:

| Что | Результат |
|---|---|
| НКД (`ACCINT`) фиксированных облигаций, 200 бумаг (ОФЗ-ПД, ОФЗ-АД, корпоративные фикс, амортизируемые, пут, колл) | 199 до копейки; 200-я — бумага с номиналом в USD на TQCB, где MOEX даёт НКД в рублях |
| Доходность к погашению (`YIELDCLOSE`, `YIELDATWAP`, публикуется до 0,01 %) | 155 из 155 бумаг в пределах округления (≤ 0,50 б.п.) |
| Доходность к оферте (`YIELDTOOFFER`, 4 знака) | 44 из 45 в пределах 0,005 б.п.; 45-я — бумага с двумя офертами через неделю (§3.3) |
| Дюрация (`DURATION`, дни) | 155 из 155 и 44 из 45 пут **точно**, после того как найдено правило MOEX: дюрация считается при опубликованной (округлённой) доходности по средневзвешенной цене |
| G-спред (`GSPREADBP`) | 552 из 564 строк точно до б.п.; остальные 12 — валютные, флоатеры и две амортизируемые, в пределах 3 б.п. |
| НКД флоатеров, **все** 466 торгуемых рублёвых флоатеров | 430 из 453 на поддержанных бенчмарках точно, 443 до копейки (новая функция 0.33.0) |
| ОФЗ-ИН (4) | НКД точно, номинал из CPI ЦБ в пределах 7,7·10⁻⁵, реальная доходность в пределах 0,5 б.п. |

**Чего не хватало под интерфейс** (всё сделано в 0.33.0, §7):

1. G-спред к КБД при дисконтировании по RUONIA OIS (решение владельца 20.10): ядро считало
   его только для бумаг на КБД, TDM брал число MOEX.
2. DM флоатеров: карточка показывает DM, ядро его не считало.
3. CS01 и базис ОФЗ–RUONIA **по срокам** (R18): ядро давало одно число, `real.js` раскладывает
   его по двум соседним бакетам приближённо.
4. НКД флоатеров: ядро требовало его в котировке, TDM считал его сам.
5. Разложение PnL флоатеров: `explain_horizon_pnl` их отвергал.
6. Оферты с окном предъявления (бриф C1): TDM выбирал оферту сам.
7. Один вызов на смешанную книгу ОФЗ и корпоративных (C8): TDM делал два.
8. Проверка, что купоны известны до горизонта (C7): ядро молча недооценивало бумагу.
9. История в масштабе (сотни бумаг × сотни дат): только скалярные функции, ~1 мс на точку.

**Что осталось** (§6): базис ОФЗ как полноценная кривая-фактор с гессианом (#111), колл по
флоатерам (#112), базисный своп КС/RUONIA одной сделкой (#113), флоатеры в векторной истории
(#114), мелочи #115–#121. Плюс данные, которые ядру должен дать бэкенд/хаб: формула каждого
флоатера (#84), CPI (#62), кривые USD SOFR / EUR €STR (#40), котировки CDS.

**Совместимость.** Всё новое выключено по умолчанию; результаты, `job_id` и закреплённые
хэши 0.32.0 не меняются. Из 414 тестов TDM с 0.33.0 проходят 411; три теста настроек падают
одинаково и с 0.32.0 — окружение, не ядро (§8).

## 2. Как TDM использует ядро сегодня

| Модуль TDM | Что берёт из ядра | Что делает сам |
|---|---|---|
| `valuation/bonds.py` | `value_portfolio` над `Instrument`/`MarketSnapshot`/`Position`, `FixedCouponLeg` / `RateAccrualCouponLeg` / `FloatingCouponLeg`, `FloatingCouponRule` с семейными конвенциями, `ExerciseAssumption.to_call`, `ShockedCurveCache` | выбор оферты с открытым окном (правило F2), заполнение неизвестных купонов, проверка полноты погашений, **НКД флоатера** (`_floater_accrued`), два вызова `value_portfolio` (ОФЗ и кредит), колл флоатера как погашение (`redeem_at_horizon`), `modified_duration = Macaulay / (1 + y)` и для флоатера |
| `valuation/fallback.py` | `BondRiskEngine` для запасной ступени (`model_price`, `par_proxy`), `kbd_effective_yield` | лестница качества оценки |
| `pnl/flash.py` | `BondRiskEngine`, `roll_curve`, `kbd_discount_curve`, `kbd_zero_rate_bp` | пошаговый флэш-PnL V0 → carry → rolldown → rates → spread → other, включая флоатеры |
| `pnl/compare.py` | `explain_horizon_pnl` | сравнение с флэшем; флоатеры ядро отвергало |
| `curves/rates.py` | бутстрап RUONIA OIS (`ois_curve_convention`, `ois_quote_periods`, `CurveBootstrapRequest`), `build_key_rate_forward_curve`, `key_rate_projection_curve`, `rebase_key_rate_curve`, `forward_curve`, `joint_calendar`, `FixingHistory` | сборка кривых из среза хаба |
| `scenario/*` | `PortfolioScenario`, `BondScenario`, `RISK_BUCKETS` | Тейлор по факторам и точный репрайсинг |
| `publish/tdm_run.py`, `api/compat.py`, `api/market_history.py`, `marketdata/history.py` | `RISK_BUCKETS`, `RISK_PILLARS`, `kbd_effective_yield`, `portfolio_result_to_json` | **G-спред — число MOEX** (`gspread_bp` из среза), спред-дюрация `−CS/PV`, денежные потоки из статических условий, точки кривых, история доходностей MOEX |
| `prototypes/concepts/lib/real.js` | — | DM флоатера = Z-спред прогона; CS01 и базис ОФЗ раскладываются **по двум соседним бакетам срока** (в прогоне одной цифрой); кривая «RUB OFZ» = КБД − RUONIA |

Наблюдения:

- Бакеты: у ядра и в прогоне `RISK_BUCKETS` = 1M, 3M, 6M, 1Y, 2Y, 3Y, 5Y, 7Y, 10Y, 15Y, 20Y+;
  демо-набор концептов (`mock.js`) рисует 3M…20Y+ с 4Y и без 1M. `real.js` берёт бакеты из
  прогона, так что на реальных данных расхождения нет; макеты стоит привести к сетке ядра.
- Флоатер: `ytm` в карточке скрыт (правильно), но `mdur` = Macaulay по прогнозным потокам —
  это не ставочная дюрация (у флоатера она около срока до следующего купона). Ставочную
  дюрацию даёт `−ΣIR / PV · 10⁴` из факторов (BACKLOG #117).

## 3. Сверка с MOEX ISS

### 3.1 Данные и метод

Публичные ответы MOEX ISS и веб-сервиса ЦБ, скачаны 21.10.2026 (~12–15 UTC):

- полные доски EOD за торговый день 20.10.2026 (`/iss/history/engines/stock/markets/bonds/boards/{TQOB,TQCB,TQOD}/securities.json?date=2026-10-20`, 3 310 строк);
- стратифицированная выборка 312 бумаг по `BONDTYPE` / `BONDSUBTYPE` / `FACEVALUE_TYPE`: все 30 ОФЗ-ПД,
  21 ОФЗ-ПК, 4 ОФЗ-ИН, 2 ОФЗ-АД, 70 корпоративных фикс до погашения, 45 амортизируемых,
  45 пут, 20 колл, 50 флоатеров, 25 валютных на TQOD; для них bondization и описание;
- **все** 445 торгуемых корпоративных флоатеров и 21 ОФЗ-ПК (bondization и описание каждого);
- КБД 20.10.2026 18:54:55 (`/iss/engines/stock/zcyc.json?date=2026-10-20`);
- живые строки `marketdata_yields` TQCB 21.10, из них 564 ещё на КБД 20.10 (по `ZCYCMOMENT`);
- RUONIA и ключевая ставка ЦБ (`DailyInfo.asmx`, `RuoniaXML`, `KeyRateXML`, 2023-11-01…2026-10-21).

Инструменты строились так же, как их строит адаптер TDM: ОФЗ — `FixedCouponLeg` (пропорционально
сумме купона), корпоративные — `RateAccrualCouponLeg(RATE_ACT_365)` со ставкой `valueprc`,
погашения после даты торгов, расчёт T+1. Флоатеры — семейные конвенции
`tests/test_moex_floater_goldens.py` (ОФЗ-ПК 29013+ — среднее RUONIA со сдвигом 6 дней, ACT/ACT;
29007–29010 — заранее, окно 6 месяцев; срочная RUONIA 3M и индекс RUONIA — сложный процент со
сдвигом 7 дней; корпоративные на КС и RUONIA — среднее со сдвигом 6 дней).

Сокращённый набор (32 бумаги всех видов, 36 тестов) закоммичен как golden:
`tests/test_moex_eod_2026_10_20_goldens.py`, фикстуры `tests/fixtures/moex_eod_2026-10-20/`
(сырые ответы, README с эндпоинтами и SHA-256). Полная выборка и прогон по всем флоатерам —
скриптами вне репозитория (по правилам ядра лицензированных и объёмных данных в нём нет);
цифры ниже — их результат.

### 3.2 Фиксированный купон

| Группа | Бумаг | НКД точно | Доходность, max \|Δ\| | Дюрация точно |
|---|---|---|---|---|
| ОФЗ-ПД | 30 | 30 | 0,47 б.п. (`YIELDCLOSE`), 0,49 (`YIELDATWAP`) | 30 |
| ОФЗ-АД (амортизируемые) | 2 | 2 | 0,49 | 2 |
| Корпоративные фикс до погашения | 67 (+3 с неизвестными купонами) | 67 | 0,50 | 67 |
| Амортизируемые | 37 (+8 с неизвестными купонами) | 36 + 1 USD-бумага | 0,49 | 37 |
| Пут (`YIELDTOOFFER`, 4 знака) | 45 | 45 | 0,005 б.п. у 44 | 44 |
| Колл (колл не исполняется, к погашению) | 19 (+1) | 19 | 0,49 | 19 |

Порог доходности — округление публикации (0,01 % = 1 б.п., то есть |Δ| ≤ 0,5 б.п.). Бумаги «с
неизвестными купонами» MOEX считает по своим допущениям; ядро их без допущения не оценивает
(и теперь может это проверить: `require_known_coupons`).

### 3.3 Правила MOEX, найденные в сверке

- **`DURATION`** — дюрация Маколея в днях при **опубликованной** `YIELDATWAP` (по средневзвешенной
  цене, округлённой до 0,01 %), округлённая до дня: 155 из 155. Не при `CLOSE`: у RU000A107PU5
  1233 дня при WAP и 1211 при закрытии. У пут — при опубликованной `YIELDTOOFFER`. Раньше
  считалось «дюрация в пределах дня»; теперь сверка точная.
- **`GSPREADBP`** — эффективная доходность минус доходность КБД на сроке дюрации (годы), на
  публикации КБД из `ZCYCMOMENT`, до б.п.: 552 из 564.
- **Две оферты через неделю без окон** (RU000A10CJ84: 19.02 и 26.02.2027): `YIELDTOOFFER` — ко
  второй (точно, 36,0104 %), `DURATION` — к первой. Похоже, первая дата — конец окна второй
  оферты, записанный отдельной строкой; адаптеру стоит передавать окна оферт
  (`Offer.window_end`), а не строки как есть.
- **`ZSPREAD` / `ZSPREADATWAPRICE`** в истории не опознаны: не б.п. и не Z-спред к КБД ни в годовой,
  ни в непрерывной конвенции (у 26238: 0,46 против −8,5 б.п. по ядру). Не сравниваем (#118).
- **TQOD рассчитывается в USD**: `ACCINT` юаневых и евро-бумаг там в долларах (постоянное
  отношение к НКД в валюте номинала), а не в валюте номинала. USD-бумаги: все 13 сходятся при
  базисе выпуска — 30/360 у замещающих, ACT/365 у новых (подтверждает BACKLOG #39: базис — условие
  выпуска, ISS его не даёт).
- **bondization `offertype`** не отличает пут от колла («Оферта», «Оферта/Погашение»): тип нужно
  брать из других полей или статических данных хаба.

Правило, найденное в сверке: **купон, определяемый в конце периода, MOEX накапливает по
реализованной формуле даже после того, как полный купон опубликован**. 13 бумаг, где
пропорция от опубликованной суммы ошибается на копейку, точны по формуле. Ядро по умолчанию
держит пропорцию для опубликованного купона: семейная формула не у каждой бумаги верна, и с
ней точных из 170 опубликованных корпоративных 157, по формуле — 155. Бэкенд с выверенной
формулой бумаги может передать текущий период без опубликованной суммы и получить цифру MOEX
(#120). Купон, известный заранее, ОФЗ-ПК накапливают пропорционально сумме (точная десятичная
арифметика: SU29008 77,49 × 13 / 182 = 5,535 → 5,54, в двоичной плавающей точке 5,534999…),
корпоративные — по ставке (RU000A108DE3: 36,39 по ставке 16,40 %, пропорция дала бы 36,40).

### 3.5 ОФЗ-ИН

SU52002–52005 на 20.10.2026 через `linkers` с CPI ЦБ (цепочка м/м до 09.2026): НКД 4 из 4 точно,
номинал в пределах 7,7·10⁻⁵ (Минфин индексирует по уровням Росстата, недоступным отсюда,
BACKLOG #62), реальная доходность в пределах 0,44 б.п. Покрывает то же, что golden 0.23.0
на 16.10, на новой дате.

### 3.6 Что не сверялось

- OIS RUONIA (кривые СПФИ на ISS только по подписке, #60), XCCY (#73), CDS (нет источника).
- USD SOFR / EUR €STR: в хабе нет кривых, ядро принимает их как готовые дисконт-факторы (#40).
- Юаневые и евро-бумаги на TQOD: единицы `ACCINT` (§3.3); на TQCB их НКД в рублях по курсу.

## 7. Что сделано в 0.33.0 и что TDM должен вызывать

Всё — поля и параметры с умолчаниями; без них поведение 0.32.0 байт в байт.

```python
from rub_fixed_income import (
    AccrualBasis, BondMetricsInput, FloatingCouponLeg, FloatingCouponPeriod, Offer,
    PortfolioScenario, ValuationPolicy, bond_metrics_batch, explain_horizon_pnl,
    kbd_effective_yields, value_portfolio,
)

policy = ValuationPolicy(
    RUONIA_OIS_CURVE_ID,
    spread_kind="credit",
    spread_kinds=tuple((i, "ofz") for i in ofz_ids),   # C8: один вызов на книгу
    g_spread_curve_id=KBD_CURVE_ID,                   # G-спред к КБД; не задавать в день без КБД
    discount_margin=True,                              # PositionValuation.discount_margin_bp
    spread_buckets=True,                               # PositionValuation.spread_buckets_rub
    require_known_coupons=True,                        # C7
    horizon="open_put",                                # C1, вместе с окнами оферт
    cap_floor_guard_bp=25.0,
)
```

| API | Что заменяет в TDM |
|---|---|
| `ValuationPolicy.spread_kinds`, `.spread_kind_for(id)` | цикл `for kind in ("ofz", "credit")` в `value_bonds`; `CS` делить по `row.spread_kind` |
| `ValuationPolicy.g_spread_curve_id`; `PositionValuation.g_spread_bp` | `gspread_bp` из среза MOEX в `tdm_run._quote_extra` |
| `ValuationPolicy.discount_margin`; `PositionValuation.discount_margin_bp`; `BondRiskEngine.discount_margin_bp()` | «DM = Z-спред прогона» в `real.js` (у флоатера на КС это разные числа) |
| `ValuationPolicy.spread_buckets`; `PositionValuation.spread_buckets_rub`; `BondRiskEngine.spread_bucket_risk(*, bump_bp=1.0, risk=None)` | разложение CS01 и базиса по двум бакетам в `real.js`; для ОФЗ — риск базиса «RUB OFZ» по срокам (R18) |
| `ValuationPolicy.require_known_coupons` | проверку в `_fill_coupons` (там, где бэкенд не подставляет купоны сам) |
| `ValuationPolicy(horizon="open_put")`; `Offer(..., window_start=, window_end=)`, `Offer.is_open(on)` | `next_offer` (правило F2) |
| `PortfolioScenario(..., spread_kind_shifts_bp=(("ofz", bp),))` | сценарий «базис ОФЗ +N б.п.» отдельно от кредитного спреда |
| `Instrument.accrued(settlement, market)`; `FloatingLeg.accrued_interest(settlement, curve=None, *, rate_basis=None)`; `FloatingCouponLeg(accrual_basis=AccrualBasis.RATE_ACT_365)` для корпоративных; `FloatingCouponPeriod(published_rate=valueprc / 100)` | `_floater_accrued`; `value_portfolio` теперь сам берёт НКД флоатера, если в котировке его нет |
| `explain_horizon_pnl(..., fixings=, end_fixings=, projection_curve=, end_projection_curve=, strike_guard_bp=)` | сравнение флэш-PnL с ядром для флоатеров (C5) |
| `bond_metrics_batch(inputs, *, kbd=None, curve=None, yield_convention=..., spread_convention=None)`; `BondMetricsInput.from_instrument(instrument, settlement, clean_pct, *, accrued_rub=None, horizon=...)`; `kbd_effective_yields(params, tenors)` | пересчёт доходности, дюрации, G- и Z-спреда за прошлые даты (c11, R24); `curve_rate` по одной бумаге |

Чтобы этим пользоваться, TDM переносит закреплённый коммит ядра на коммит 0.33.0
(`rub-fixed-income-core==0.33.0` в зависимостях — сейчас там `==0.32.0`).

## 8. Совместимость: тесты TDM

Снимок ветки TDM `9647e37` (`git archive`, репозиторий TDM не тронут) в двух одинаковых
окружениях Python 3.12: с ядром `c0af388` (0.32.0) и с рабочим деревом 0.33.0; бэкенд
ставился без зависимостей из `tool.uv.sources` (`--no-sources`), остальное — по
`backend/pyproject.toml`.

Итог: **из 414 тестов TDM с 0.33.0 проходят 411; 3 падают одинаково с 0.32.0** —
`test_settings.py::test_defaults_without_env_file`, `::test_inbox_and_adapter_settings`,
`test_settings_home.py::test_desk_home_resolution` (путь к каталогу данных при запуске из
снимка вне рабочей копии), к ядру отношения не имеют.

- Тесты без базы данных одинаково зелёные с обеими версиями с первого прогона.
- Тесты с базой (встроенный PostgreSQL `pgserver`) в этой среде нестабильны с **обеими**
  версиями: параллельные прогоны другой сессии на той же машине делят каталоги `pgserver` и
  чистят чужие временные каталоги pytest, отсюда `could not access file "$libdir/plpgsql"` и
  `PermissionError` на `pg_ctl`. Поэтому каждый файл гонялся отдельным процессом со своим
  `--basetemp`, а упавшие тесты — повторно до трёх раз с каждой версией: все, кроме трёх
  тестов настроек, проходят с 0.33.0 (с 0.32.0 часть так и не прошла за три попытки — то
  же окружение).

Ядро: 1309 тестов (было 1250), `ruff`, `mypy --strict` на 3.11, сборка — зелёные.

## 9. Что осталось и почему

- **#111, базис как кривая-фактор.** Первый порядок по срокам и параллельный сценарий уже
  есть; гессиан и сценарии по бакетам базиса требуют разделить у флоатера на одной кривой
  роли дисконтирования и проекции (сейчас один фактор) и договориться об именах факторов в
  контракте результата v2/v3. Это решение контракта, а не только код.
- **#113, базисный своп.** Нет в книге на реальных данных; двумя свопами считается уже сейчас.
- **#112, колл флоатера.** TDM погашает такой флоатер на дату колла сам — экономически то же.
- **Данные** (#84 формула флоатера, #62 CPI, #40 кривые SOFR/€STR, #39 базис валютных бумаг,
  котировки CDS) — работа хаба и бэкенда; ядро готово их принять.
- **Скорость тяжёлых движков** (#86, #106): гессиан флоатеров 50–70 мс на позицию; ускорение
  меняет последний бит — нужна новая версия модели.
